## 1. 起点:我到底卡在哪

我最初的原话:

> 即使是这个课程很详细,老师会带着做项目,我还是对于很多操作的流程一知半解。

拆开看,这句话里其实混了**四个不同维度**的提问。混在一起问,就会越想越乱:

| 我嘴上的问题 | 它其实在问 | 答案的来源 |
|---|---|---|
| 为什么要有这一步? | 它在**防哪种失败**? | 风险维度 |
| 它是怎么来的? | 哪次**事故/痛点**催生了它? | 历史维度 |
| 它到底在干嘛? | 它站在**请求链路的哪个位置**? | 结构维度 |
| 我以后还要用吗? | 换掉技术栈,它**还成立吗**? | 抽象维度 |

**记住这四问,就不需要"听懂老师的每一句话"了** —— 只需要能把任何一步放进这四个格子里。放不进去,才是真的没懂。

## 2. 全栈项目只有四种活动

课程按零件讲,让人以为在背零件目录。但真实的项目只在做四件事:

| 活动 | 产出物 | 判断标准 |
|---|---|---|
| 1. 把模糊需求变成**可验证的约定** | 数据模型、接口文档、验收标准 | 产出是"文档/契约" |
| 2. 把约定变成**能跑的代码** | 代码、配置 | 产出是"能运行的东西" |
| 3. 证明代码**真的符合约定** | 测试、CI 红灯 | 产出是"断言/流水线" |
| 4. 把代码**安全送上生产并盯着它** | 部署脚本、日志、监控 | 产出是"线上可观测性" |

任何一节课的任何一个 part,都属于这四类之一。**当一个 part 让你困惑时,先问:它产出的是什么?** 如果它什么可验证的东西都没产出,那它大概率是老师为了教学便利加的脚手架 —— 这类东西可以放心"看懂就忘"。

---

## 3. 每个 part 都是"事故的化石"

这是我认为最有用的一张表。左边是课上的步骤,中间是它当年被什么事故逼出来的,右边是它在我自己的项目里还留不留。

| 你看到的 part | 它防的事故 | 自己项目还要吗 |
|---|---|---|
| `.env` / 环境变量 | 数据库密码被 push 到 GitHub,机器被拿去挖矿 | **永远要**,第一天就要 |
| Git 分支 + 小步提交 | 改崩了想回退,发现没有可回退的点 | **永远要** |
| 数据库 migration | 手动在生产库改表结构,改错无法回滚 | **要**,除非是玩具 |
| API 契约 / 接口文档 | 前后端各写各的,联调时字段对不上 | **要**,可以先写约定再写代码 |
| 测试 | 改 A 弄坏 B,没人发现,用户先发现 | **要**,但不追求覆盖率 |
| CI(流水线) | 本地能跑,服务器上少装一个包就挂 | **要**,这是"能部署"和"敢部署"的分界 |
| Docker | "在我电脑上明明是好的" | 可选,强烈建议 |
| Nginx / 反向代理 | 前端要同域、要 HTTPS、要扛并发 | **要**(或云平台代劳) |
| Redis / 缓存 | 一个查询把数据库打满,整站 502 | 按需 |
| 日志 / 监控告警 | 用户说"打不开",你连从哪查起都不知道 | **要**,最小版本是错误上报 + 健康检查 |
| 分页 / 限流 | 一个接口被爬虫刷穿 | 上线前要 |
| 事务 / 幂等 | 转账扣了钱没加钱;连点两下下了两单 | **要** |

**规律:技术会过时,事故不会。**
所以学一个 part 的正确姿势是记住"它防什么",而不是记住它的写法。写法三年换一遍,风险清单二十年不变。

## 4. 把 part 串起来:一条请求走完全程

这是回答"作用是什么"最有效的方法。用"一次转账/下单"举例:

```
① 用户点"确认"
   前端:组件 → 表单校验 → 状态管理（loading，防重复提交）

② 浏览器发 HTTP 请求
   → 带 token（你是谁）、带请求体

③ 请求先到 Nginx / 网关，不进业务代码
   → 解 HTTPS、限流、转发、返回静态资源

④ 后端:路由 → 中间件 → 控制器 → 服务层
   中间件先做统一的事:验 token、记日志、解析请求体

⑤ 数据层:开事务
   扣款 + 入账必须同时成功；走索引查账户

⑥ 返回:序列化 JSON → 状态码 → 前端
   前端按状态码分支渲染:成功 / 余额不足 / 网络异常

⑦ 旁路（不在这条链路上，但同样重要）
   日志、监控、缓存、消息队列、定时任务
```

那些"突然出现"的 part,都是这条链路上的某个工位。
**心里有这条线,任何新概念都能问:"你站在第几步?"**

## 5. 判断"通用不通用":三问 + 三桶

不要问"这个重要吗"(所有东西都重要),要问这三个:

1. **删掉它,项目还能跑吗?** → 能跑但会出事 = 它是"防护措施",不是"功能"。
2. **它保护的是哪种失败?** → 答不出来,说明你只是抄了命令。
3. **换一个技术栈,它还在吗?** → 还在 = 学**本质**;消失了 = 学**目的**,别背语法。

| 桶 | 内容 |
|---|---|
| **桶一:永久通用,形态稳定** | 版本控制、依赖管理、环境与密钥、目录结构、错误处理、日志、README、部署流程 |
| **桶二:多数项目要,按需裁剪** | 迁移、鉴权、接口文档、测试、CI/CD、监控、缓存 |
| **桶三:课程/框架特有,可以忘** | 脚手架命令、为讲概念做的重构、模板代码、演示假数据 |

课程最坑的地方,是把三个桶混在一起按顺序讲,让人以为它们同等重要。

## 6. 自己做项目,真正要关心的十个决策点

新手想要"步骤清单",但清单换个项目就作废。资深做法是关心**决策点**:

| 决策点 | 常见错误 | 最小可行做法 |
|---|---|---|
| 1. 什么算"做完" | 边写边加需求,永远收不了尾 | 先写 3 条验收标准 |
| 2. 技术选型 | 追新的、追多的 | 选**最熟**的、**部署最便宜**的 |
| 3. **数据模型** | 一上来写页面,表结构边写边改 | 先画表和关系 |
| 4. 接口契约 | 前后端同时开写,联调时爆炸 | 先定 URL / 入参 / 出参 / 错误码 |
| 5. **先打通一条竖线** | 10 个功能各做 50% | 只做 1 个功能,从 UI 通到数据库、再上线 |
| 6. 提交节奏 | 攒一天一次大提交 | 一个小功能一次提交 |
| 7. 测试重点 | 追求覆盖率数字 | 测**失败路径**:空值、越权、重复提交、超时 |
| 8. 密钥与配置 | 硬编码,提交进仓库 | `.env` + `.gitignore`,线上用平台环境变量 |
| 9. 部署时机 | 全做完再部署 | **第一天就部署一个 Hello World** |
| 10. 可观测性 | 出了事靠 `console.log` | 结构化日志 + 错误上报 + `/health` |

> 第 5 条(vertical slice)是课程最容易让人错过的东西。课程为了讲清楚,会"先把前端讲完再讲后端",而真实项目必须反过来:**先让一条数据从手指头走到磁盘再走回来。**

### 还有一组"横切关注点"

课程很少单独开一章,但一上真实项目就会被它们打脸:

输入校验、权限(不只是"登录了",而是"这个人能不能动这条数据")、事务与一致性、幂等、并发、分页、时区、**金额用整数分或 Decimal 存,绝不用浮点**。

最后这条,我有天然优势,别丢。

## 7. 我自己的项目:13 层楼是怎么盖起来的

项目的 19 个提交,就是一张设计图。**每一层都是被上一层留下的具体麻烦逼出来的。**

| 层 | 撞到的墙 | 拿起的工具 |
|---|---|---|
| 1 | 什么都没有,先要能看见东西 | HTML + CSS + JS |
| 2 | 全挤在一个文件里,改不动 | 拆成多个文件 |
| 3 | 文件之间没法引用,只能靠顺序 | npm + vite |
| 4 | 数据一变,得亲手改页面 | React |
| 5 | 按 F5 就回首页了 | 手写路由 |
| 6 | 手写路由太累,外壳还要自己拼 | Next.js |
| 7 | 不想在服务器上跑 Node | 静态导出 |
| 8 | 静态文件不会查数据库 | 手搓 HTTP 服务 |
| 9 | 手搓的四个毛病受不了 | FastAPI |
| 10 | 浏览器把请求拦下来了 | CORS |
| 11 | 结果是假的;重启数据就没了 | snownlp + SQLite |
| 12 | 所有人看到同一份历史 | cookie 会话 |
| 13 | 地址写死在代码里 | .env + 部署 |

### 每一层留下的可迁移知识

- **第 1–2 层**:`<script>` 要放 `</body>` 前(要等元素存在);拆文件后暴露两个新问题——**重复**和**顺序/全局**。
- **第 3 层**:三件套分工 —— `package.json`(购物清单,进 git)、`node_modules/`(真货,**不进** git)、`package-lock.json`(精确小票,**必须**进 git)。`npm run xxx` = 执行 `scripts` 里的 `xxx`。
- **第 4 层**:组件 = 返回页面的函数;props = 父传子只读;state = 自己记着会变的值。**只能通过 `setText` 改,不能直接改** —— 这是 React 能知道数据变了的根本原因。
- **第 5 层**:"我在哪一页"不该记在内存里(`useState`),该记在**地址栏**里。`pushState` + `popstate`。**这层要记的是"为什么存在",不是代码。**
- **第 6 层**:文件夹 = 路由;`layout.jsx` 当外壳;`"use client"` = 这个文件交给浏览器执行(用到 `useState`/`onClick`/`window` 就得写)。
- **第 7 层**:**前后端为什么是两个进程** —— `output: 'export'` 产出纯静态文件,而静态文件**不会查数据库**,所以必须另有一个后端。这一行配置是整个架构的分水岭。
- **第 8 层**:**手搓一遍 HTTP 的价值在"拆黑盒"**。它的四个毛病(靠 if 判 URL / 无校验 / 无文档 / 单请求)正好对应框架的四个功能。
- **第 9 层**:FastAPI 只负责"路由表 + 校验",真正监听端口的是 **uvicorn**;`fastapi dev` 就是"帮我把 uvicorn 起起来"。自动文档在 `/docs`。
- **第 10 层**:同源 = 协议 + 域名 + 端口;**预检 OPTIONS**;`credentials: "include"` 和 `allow_credentials=True` 必须**两边同时**表态,漏一边 cookie 静默丢失。
- **第 11 层**:`?` 占位符防 SQL 注入;一个请求一个连接最简单;索引要按查询形状加。
- **第 12 层**:**存包牌模型**。`HttpOnly` 防脚本偷牌,`SameSite` 防别的站乱带。**这是"设备号",不是"账号"。**
- **第 13 层**:代码一份,配置多份;`.env` 不进 git,`.env.example` 进。

## 8. Git:从"会点按钮"到"知道在干嘛"

### 三个概念先分清

| | Git | GitHub |
|---|---|---|
| 是什么 | 装在**自己电脑上**的软件 | 一个**网站** |
| 干什么 | 记录每次改动、能回到任何一天 | 把仓库放一份到云上 |
| 要联网吗 | 不用 | 要 |
| 可替换吗 | 只有这一个 | GitLab、Gitee、自建都能换 |

**"服务器上没有编辑器"只对了一半** —— Linux 服务器上几乎都有 vim/nano。真正的原因是:

1. 在服务器上手改的代码**不在版本控制里**,改坏了没法回退
2. 服务器会慢慢**偏离仓库**,下次 `git pull` 就冲突
3. 服务器重建那天,手改的东西**全没了**

> **规矩:服务器上只"取",不"改"。** 本地 → commit → push → 服务器 pull。

### 一个文件要走过四个地方

```
① 工作区           ② 暂存区            ③ 本地仓库         ④ 远程仓库
你编辑的文件   →   准备好的清单    →    提交历史      →   GitHub
   (改了)          (git add)         (git commit)       (git push)
```

**为什么要有暂存区?** 因为一次提交应该是**一件事**。改了三个文件(修 bug / 加功能 / 改标点),可以只把前两个放进篮子提交一次。**暂存区就是那个挑菜的篮子。**

### 六条命令

```bash
git status                  # 永远先敲这个，它会告诉你下一步该敲什么
git diff                    # 提交前看一眼，拦住 80% 的"我怎么会提交了这个"
git add <文件>              # 放进篮子（不产生版本）
git commit -m "为什么改"    # 真正存成一个版本
git push                    # 推到 GitHub
git log --oneline           # 看历史
```

### 判断推没推

```bash
Your branch is ahead of 'origin/main' by 1 commit.   # 本地多一版，赶紧 push
Your branch is up to date with 'origin/main'.        # 三边一致，可以收工
nothing to commit, working tree clean
```

### 撤销:两种最常用的

```bash
git restore 文件名              # 扔掉未提交的改动（不可恢复）
git restore --staged 文件名     # 只从篮子里拿出来，内容不动（安全）
```

### "退回到之前的版本"其实是五件事

| 我想干嘛 | 会不会丢代码 | GitHub Desktop 里 |
|---|---|---|
| 想**看看**旧版本 | 不会 | History 标签 → 点提交 |
| 扔掉**没提交**的改动 | **会丢** | Changes → 右键 → Discard |
| 补最后一笔 | 不会 | 右键最新提交 → Amend |
| 撤提交、**留改动** | 不会 | Reset → **Keep changes** |
| 撤提交、**没推送** | **会丢后面几版** | Reset → **Discard** |
| 撤提交、**已推送** | 不会 | **Revert changes in commit** ← 只有这条安全 |

**选择标准只有一条:这个提交推上 GitHub 了吗?**

- 没推 → 可以 **Reset**(改写本地历史,干净)
- 推了 → 只能 **Revert**(生成一个反向提交,历史只增不改)

### Revert 和 Reset 的实际差别

```
Revert 之后：历史变长，原来那条还在
cfb7f28 第三版：改成 v3
7a1c9f4 Revert "第三版：改成 v3"    ← 多出来的一条
文件内容回到了 v2

Reset 之后：历史变短，后面几版从列表消失
5178f22 第一版：写好 v1
文件内容回到了 v1
```

**Revert 诚实,Reset 干净。** 代价是:已推送还 Reset,就得 force push,会抹掉远程历史,别人拉过就乱。

### 后悔药

```bash
git reflog                        # 记录 HEAD 的每一次移动
git reset --hard <那串号码>       # 甚至连 reset --hard 掉的都能捞回来
```

**Git 里几乎不存在"真的丢了"**,除非连 `.git` 文件夹一起删。所以可以放心练。

### 最安全的练习方式

**开一个分支练。** 分支 = 平行宇宙。搞砸了切回 `main`、删掉分支,`main` 一根头发都没掉。

### commit message 怎么写

**写"为什么",不写"改了什么"。** 因为 `git diff` 已经能看出改了什么。

```
差：update
好：历史记录按 session 隔离，修掉所有人看到同一份的问题
```

## 9. 部署:从"能跑"到"能一直跑"

### 7.1 留下的三笔账

| 三笔账 | 说白了是什么 |
|---|---|
| ① 后端服务脆弱 | `nohup` 扔后台:崩了不重启、开机不自启、状态要自己捞进程号 |
| ② 8000 端口裸奔 | 后端直接对全网敞开,连 `/docs` 都能被点开 |
| ③ 前后端不同源 | 前端 80、后端 8000,两个端口 = 两个源,全靠 CORS 调停 |

### 7.2 第一笔:systemd 取代 nohup

**`nohup` 只解决"不占终端",不解决"有人管"。**

| 谁 | 管什么 |
|---|---|
| 程序自带命令（`sudo nginx`、`fastapi run`） | 怎么起、怎么停 |
| **systemd** | 开机拉起、崩了重启、收日志 |

service 文件永远三段:`[Unit]` 是什么服务 / `[Service]` 怎么跑 / `[Install]` 何时带起来。

```ini
[Unit]
Description=zero-to-tech backend
[Service]
User=ubuntu
WorkingDirectory=/home/ubuntu/zero-to-tech/backend
ExecStart=/home/ubuntu/zero-to-tech/backend/.venv/bin/fastapi run
Restart=always
[Install]
WantedBy=multi-user.target
```

三个必须注意的点:

- `User` 不写默认用 **root** —— 最小权限原则,够用就好
- `WorkingDirectory` **必须绝对路径**
- `ExecStart` 里**不要写 activate**,直接写 `.venv/bin/fastapi` 的绝对路径

```bash
sudo systemctl daemon-reload          # 改了 service 文件必须 reload，最容易忘
sudo systemctl start zero-backend
sudo systemctl status zero-backend    # 看到 active (running)
sudo systemctl enable zero-backend    # 开机自启
```

**亲手做一次崩溃自愈实验:** `sudo kill <Main PID>` → 再 `status`,还是 `active (running)`,但 PID 换了。这就是 `Restart=always`。

> ⚠️ `systemctl stop` 和 `kill` 不一样:**stop 是真停,不会自动拉起。**

**日志三代:**

| 形态 | 做法 | 问题 |
|---|---|---|
| ① 终端实时 | `fastapi dev` 占着窗口 | 窗口一关,全没了 |
| ② 写进文件 | `nohup ... > backend.log 2>&1 &` | 要自己管:叫啥、放哪、何时清、会一直涨 |
| ③ 交给 systemd | `journalctl -u zero-backend` | 有人管,有容量上限,旧的自动清理 |

```bash
journalctl -u zero-backend -n 50    # 最后 50 行
journalctl -u zero-backend -f       # 实时跟随（光标停住不是卡住，是在等）
```

**记得把 `backend.log` 删掉** —— 它已经是一份永远不会再更新的旧账,留着只会骗到以后的自己。

### 7.2 第二笔:反向代理

> **Nginx 擅长"对外",Uvicorn 擅长"算"。**

| | Nginx | Uvicorn |
|---|---|---|
| 访客日志 | 逐条记来源、浏览器、字节数 | 没有单独的一份 |
| 加密 HTTPS | 一条命令 | 要自己塞证书、自己管续期 |
| 提速(压缩/缓存) | 现成开关 | 没有 |
| 挡在最前面 | 二十多年的主业 | 能胜任,但是"兼职" |

**两种日志要分清:**

- **运行日志**(程序在干嘛、有没有报错)→ systemd 的 `journalctl`
- **访问日志**(谁来过、从哪来、什么浏览器)→ Nginx 的 `/var/log/nginx/access.log`

**关键决策:不是 Nginx 也监听 8000,而是按路径分工。**

```
前端 URL:  /            /text-lab
后端 URL:  /api/profile /api/analyze /api/history
```

```nginx
location /api/ {
    proxy_pass http://127.0.0.1:8000;          # ⚠️ 末尾千万别加斜杠，加了全线 404
    proxy_set_header Host $host;                # 访客敲的是哪个地址
    proxy_set_header X-Real-IP $remote_addr;    # 访客真实 IP
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme; # 走的是 http 还是 https
}
```

四行 `proxy_set_header` 的原因:**转手一次,有些信息会丢。**(`X-` 是老约定,表示非标准头。)

**顺带解决一个隐患**:`/docs` 不是 `/api/` 开头,会被解析到 `location /`,静态目录里找不到 → 404,**从公网够不着了**。

**反向代理** = 站在**服务器**一侧转发。站在使用者一侧的(公司要求员工上网先过代理)叫**正向代理**。

**让 8000 不对外,要砍两刀:**

1. **屋里**:`ExecStart` 加 `--host 127.0.0.1`(默认是 `0.0.0.0`)
2. **屋外**:云控制台安全组删掉 8000

> 这叫**纵深防御** —— 别把安全押在单独一道防线上。

### 7.2 第三笔:前端留空

```
NEXT_PUBLIC_API_BASE_URL=        # 留空
```

留空之后 `${API}/api/profile` 变成 `/api/profile` —— **相对路径**,浏览器自动补上当前页面的源。

**为什么值钱:** 后面还要把 IP 换成域名、http 换成 https,**留空就不必再改前端配置**。

改完必须 `npm run build`(配置是构建时烧进 JS 的)。

### 验证三处

| 看哪里 | 应该看到 |
|---|---|
| 同源 | Network 里不再有 `OPTIONS`,只剩一条干净的 POST |
| 8000 关闭 | 本地访问 `http://服务器IP:8000/...` 连不上 |
| 自愈 | 关 SSH 照常;kill 掉会重启;**重启整台服务器还会起来** |

> **"用户那一侧什么都没变,底下的地基却整个换了一遍。好的重构就该这样。"**

⚠️ **`CORSMiddleware` 和 `credentials: "include"` 千万别删** —— 线上不需要了,但**本地 3000 → 8000 依然跨源**。`ALLOWED_ORIGINS` 同理:代码里 `os.getenv()` 取不到会直接报错。

### 7.3:域名与 HTTPS

**顺序不能反**:证书是签给**域名**的,所以先有域名,再上 HTTPS。

**域名从右往左读**,买的是"在某个 TLD 底下占一个名字"的登记权,子域名免费。

**最该记住的一句:DNS 眼里 `example.com` 和 `www.example.com` 是两个不同的名字**,要各配一条 A 记录。

| 类型 | 登记什么 | 你用吗 |
|---|---|---|
| **A** | 名字 → IPv4 | **就用它** |
| CNAME | 名字是另一个名字的别名 | 指向第三方时用 |
| MX | 邮件交给谁 | 收发邮件 |
| TXT | 一段文本 | 证明"域名是我的" |

**ICP 备案的判断标准只有一条:看服务器在哪,不看域名在哪买。** 大陆服务器必须备案;备案期间 80/443 会被拦,网站通过域名打不开。

**Nginx 凭什么"认"域名?** 请求到 80,看 `Host` 头和每个 `server{}` 的 `server_name` 比对,对上谁交给谁;**全对不上,交给标了 `default_server` 的兜底块**。我之前能用 IP 访问,纯粹是因为有个"来者不拒"的兜底配置。

**HTTPS = HTTP + 加密层**,解决三件事:加密、防篡改、身份。

**关键认知:HTTPS 没有改写 HTTP,而是在前面先加了一次握手。** 握手只做一次,同一条连接上后续请求直接复用。

**两份文件,一公一私:**

| 文件 | 作用 | 保密 |
|---|---|---|
| 证书 `.pem` | 握手时发给每一位访客 | 公开 |
| 私钥 `privkey.pem` | 握手时当场签名 | **永不离开服务器** |

**谁拿到私钥,谁就能冒充你的网站。** 不要 `cat`、不要截图、不要提交进 Git。

**一条命令搞定:**

```bash
sudo snap install --classic certbot
sudo certbot --nginx          # 生成私钥 → 申请 → 验证 → 领证书 → 改 Nginx → reload
sudo certbot renew --dry-run  # 彩排一次续期
```

它会把 Nginx 改成 `listen 443 ssl` + 两行 pem 路径,并**新加一个小 server 块守着 80,回 301 送去 https**。

> 顺带补全状态码最后一家族:**3xx = 重定向**。

**最精妙的一处:给 cookie 补 `Secure`。**

1. HTTPS 加密的是**链路**;cookie 带不带,归**浏览器**管
2. 浏览器只看域名对不对,默认**不看协议**
3. 访客点一个 `http://` 老链接 → 纸条照样被带出去,**在明文路上送了一遍**
4. Nginx 确实回了 301,但 **301 是到了服务器才回的,纸条早被看过了**

> **HTTPS 管得了它自己那条路,管不了纸条走哪条路。**

```python
response.set_cookie(
    "session_id", sid,
    httponly=True, samesite="lax",
    secure=True,        # ← 只在 HTTPS 上运送
    max_age=60 * 60 * 24 * 30,
)
```

**三属性的分工:**

| 属性 | 挡的是谁 |
|---|---|
| `HttpOnly` | 页面里的 JS —— 纸条它读不到 |
| `Secure` | 明文的路 —— 没加密就不发 |
| `SameSite` | 别的站点 —— 不是我这儿发起的请求别乱带 |

> **为什么 6.6 那时候不加?** 因为那时只有 HTTP 一条路,加了纸条就送不出去。
> **有些配置要先等条件具备,并非"早知道就该加"。**

⚠️ 加完代码刷新页面,`Secure` 不会自己打勾 —— **cookie 属性是发纸条那一刻写死的**,旧纸条还在,后端就不重发。要 `F12 → Application → Cookies` 删掉 `session_id`,再刷新。

本地 `localhost` 有特殊照顾,带 `Secure` 的 cookie 照发。

## 11. 我最想长期记住的 15 条

1. **工程实践几乎都是事故驱动的。** 每个规范背后都有人被坑过。
2. **技术会过时,事故不会。** 学 part 要记住"它防什么"。
3. **改代码便宜,改数据模型极贵。** 先想清楚表结构。
4. **输入校验永远是第一道风控。**
5. **接口要幂等,部署脚本也要幂等。** 重复执行结果应当一致。
6. **服务器上只"取",不"改"。**
7. **文件传输只传"现在",版本控制传"现在 + 来路"。**
8. **推送过的历史不要改写。** 用 revert,不用 reset。
9. **代码一份,配置多份。** 不同的只是环境。
10. **`NEXT_PUBLIC_` 是构建期常量**,不是运行时读的。
11. **凡是读文件、找配置、存数据,一律以脚本自身位置为基准**,别信当前目录。
12. **同源 = 协议 + 域名 + 端口。** 三者齐了才叫同源。
13. **纵深防御:别把安全押在一道防线上。**
14. **单一数据源。** 同一份内容存两处,迟早不一致。
15. **一份过时的 README 比没有更糟。**

### 三个可以反复用的动作

**① 遇到任何新工具,只问一句:**

> "它补的是上一个东西留下的哪个麻烦?"

**② 每看完一节课,填一张三行卡:**

```
这一步防的是哪种失败？
它的输入 → 输出是什么？（说不出来 = 没懂）
换个项目/换个技术栈，它还成立吗？
```

攒够 30 张,就有了一张比课程更好的地图。填不出来的那几张,恰好就是以为懂了其实没懂的地方。

**③ 卡住时把黑盒画成 `输入 → [黑盒] → 输出`,先只关心契约。**

## 13. 关于"和 AI agent 一起学"这件事

这四天的对话里,有几个观察值得记下来:

**1. 提问的颗粒度,决定回答的可用度。**
"这个项目是怎么来的"是个好问题;"git 怎么提交"也是个好问题。但"太专业了不够清晰"这类反馈同样重要 —— 它把回答从"给同行看的摘要"拉回"给初学者看的教程"。

**2. 给上下文,比给问题更重要。**
把 `README.md` 的路径给出来,对方才能读到 git log、代码、配置、构建产物,而不是只能给通用建议。**通用建议听起来都对,但用不上。**

**3. 最好的回答不是结论,是因果链。**
"用 systemd" 是结论;"nohup 崩了不重启、开机不自启,所以需要进程守护" 是因果链。结论过时,因果链不会。

**4. 要敢于说"这段我懂了,换个讲法"。**
第 3 轮那句"还是太专业了,像教初学者一样",是整个对话质量的分水岭。

**5. 让 AI 去读真实文件,而不是替你回忆。**
"我看过你的项目"和"我读了你的 19 个提交、6 个组件、3 个后端文件"是两回事。前者是客套,后者能指出 `storage.py` 里那个索引为什么加对了。
